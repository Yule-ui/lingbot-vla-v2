# 四卡 4090 推荐训练方案

## 推荐结论

首选：**两路真实相机＋640×480＋解冻 VLM 语言最后四层＋动作专家训练＋FSDP2/BF16/梯度检查点，关闭 activation offload，启用可扩展显存分配**。

相对上一轮实测方案，去掉始终被 mask 的右腕相机占位，不丢弃真实观测；配合 allocator 设置减少显存碎片，避免 activation offload 的传输成本。

2026-10-16 在本机四张 RTX 4090 上，每个 rank 完成 6 个 optimizer step：

| 指标 | 之前：三槽输入、四层、offload | 推荐：两槽输入、四层、expandable segments |
|---|---:|---:|
| 两路实际 RGB 分辨率 | 640×480 | 640×480 |
| 可训练参数 | 约 23.42 亿 | 约 23.42 亿 |
| 单卡最大 allocated | 18.729GiB | 19.972GiB |
| 单卡最大 reserved | 21.943GiB | 21.895GiB |
| 驱动采样占用峰值 | 22.637GiB | 22.588GiB |
| 最小采样余量 | 1384MiB | 1434MiB |
| 跳过前两步后的中位耗时 | 29.113 秒／步 | 18.119 秒／步 |
| 抽检梯度有限、参数更新、无 OOM | 通过 | 通过 |

短跑耗时减少约 38%，不代表最终任务成功率已经提升。所有驱动峰值均为每秒采样，可能漏掉更短的峰值；本次没有测量 checkpoint/HF 导出的额外峰值。

## 正式参数建议

| 项目 | 建议 |
|---|---|
| 起点 | `/data-teamA/models/lingbot-vla-v2-6b` |
| 数据 | `/data-teamA/datasets/ur3_eef_relative_20261016`，保持独立的 81／9 轨迹划分 |
| 相机 | `camera_top`、`camera_wrist_left`，训练与推理一致 |
| 输入 | `image_width: 640`、`image_height: 480` |
| VLM | 解冻语言层 32～35；视觉编码器、词嵌入及前 32 层冻结 |
| 动作专家／投影／辅助头 | 继续训练 |
| LR | VLM `1e-6`；动作专家 `1e-5`；投影／辅助头 `2e-5` |
| MoE LR 自动倍率 | 关闭 |
| AdamW | betas=`(0.9,0.95)`；正式候选 weight decay=`0.01`，bias／一维参数不衰减 |
| 调度 | 固定预热 150 步，之后 constant，便于分段恢复 |
| 并行／精度 | 四卡 FSDP2 全分片、BF16、梯度检查点 |
| Batch | 每卡 1、累积 4、全局 16 |
| CPU offload／整模型 compile | 首轮关闭 |
| Action chunk | 保持 50，不同时改变控制时间窗 |
| 辅助损失 | 保留当前深度、未来深度及视频模块，主要权重继续使用 0.004 |
| Checkpoint | 每 2500 步保存 DCP＋HF，按验证效果选模型 |

环境设置应在 Python 启动前生效：

```bash
export PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True
```

该选项是 PyTorch 的实验性 allocator 设置；这里的推荐依据是本机实际短跑，而不是保证所有硬件都同样有效。[PyTorch 官方说明](https://docs.pytorch.org/docs/2.8/notes/cuda.html#cuda-memory-management)

候选配置：[train_two_views_640.yaml](../configs/vla/ur3_20261016/train_two_views_640.yaml)。使用时必须通过 `tools/run_ur3.py --stage train --vlm-train-last-layers 4`，并传入新 manifest。旧 `tools/start_ur3.sh train` 仍读取旧数据配置，不能作为新方案启动命令。

候选配置将 weight decay 从显存短跑的 0 调整到 0.01，并为 bias／一维参数排除衰减；这些正式超参数仍需保存／恢复试跑验证，不能把显存短跑视为完整长训验收。

## 分段训练与选择模型

先做 50～100 步正式配置试跑，覆盖 optimizer、DCP/HF 保存和恢复。试跑使用独立输出目录；验证后清理试跑大权重，保留报告，避免占用正式训练磁盘预算。

正式训练从原始预训练权重开始，后续各阶段从同一新运行的 checkpoint 恢复：

| 累计步数 | 遍历训练集 | 纯训练时间估算 | `lr_warmup_ratio` |
|---|---:|---:|---:|
| 2500 | 1.09 遍 | 约 12.6 小时 | 0.06 |
| 5000 | 2.18 遍 | 约 25.2 小时 | 0.03 |
| 10000 | 4.36 遍 | 约 50.3 小时 | 0.015 |

上述 ratio 保持所有阶段的预热步数都是 150；后续从已保存的 optimizer/scheduler 状态恢复，不重新预热，也不重新从预训练起点开始。时间根据 6 步短跑折算，不含保存、评估和长期负载变化。

2500 步结束时释放训练显存再评估；通过后恢复到 5000。只有验证及真机表现仍在改善时才延长到 10000。不建议在四卡训练期间另启一个完整 GPU 推理服务。

按此前估算，每份四层微调 DCP＋HF 约 53GiB；保留 2500／5000／7500／10000 四份约 212GiB，当前约 293GiB 空间具备预算余量。正式保存后需核对实际大小，当前程序没有自动保留上限，不能自行将频率改为每 1000 步并长期保留全部权重。

## 必须针对“空抓”验证的内容

1. **执行映射**：此前数据中，命令位移与实测位移在滞后 1 帧时相关性很高，但比例约 0.254。核对采集与推理的增益、平滑、限幅、25Hz 时序、base 平移和局部四元数乘法。不要凭比例直接缩放标签。
2. **视觉依赖**：在相近机械臂起始姿态下，改变目标方块位置，检查预测首段轨迹是否朝对应位置改变；再改变任务文本，检查目标选择。输出发生变化本身不能证明定位正确。
3. **独立验证**：保留当前 9 条验证轨迹，分别统计三项任务的位移、旋转和夹爪误差，与不移动／保持夹爪基线比较。训练 loss 不能作为唯一的 checkpoint 选择依据。
4. **新摆位闭环**：对三个任务分别做约 10 次不同布局的闭环验证，记录成功率、错误目标、抓取偏差和夹爪时机。部署端使用本次相同的两路相机和 640×480 预处理。
5. **数据覆盖**：若演示摆位重复，优先补充不同方块位置、相同颜色干扰物和抓取接近阶段的成功演示。追加数据后建立新划分、只用训练集重新计算归一化，不覆盖旧模型依赖的统计文件。

新 task_index 映射为：0→block 2，1→block 0，2→block 6。推理优先传入对应任务文本，避免沿用旧数据的编号表。

如果执行映射无误、数据覆盖足够，而 5000 步后仍缺乏正确视觉响应，再做视觉 merger／视觉后层 LoRA 对照；这需要新一轮实现和显存验证。首轮不扩大到整套 VLM 全量训练。

完整实测：[显存报告](ur3_640x480_memory_measurement.md)、[逐 rank 汇总 JSON](ur3_640x480_memory_measurement.json)。本方案尚未启动正式长训。
